# PLAN 71: Public AWS Deployment

## Goal

Prepare Trailbook for gradual public deployment on AWS:

- S3 for waypoint photos and binary media;
- RDS PostgreSQL for production data;
- ECS Fargate for the NestJS API;
- Amplify Hosting for the NextJS web app;
- CloudWatch for logs and operational visibility;
- Route 53 + ACM for domain and HTTPS.

The rollout must be incremental. Each phase should be deployable and testable
without forcing the next phase.

## Decisions

- Start with S3 only while the API and database can still run locally.
- Keep the backend as the authority for auth, ownership, metadata and access.
- Mobile must never receive AWS credentials.
- Mobile uploads media directly to S3 only through short-lived presigned URLs.
- Production deployment should not depend on MinIO. MinIO remains local/dev only.
- Use one AWS environment first: `production`. Add `staging` later if needed.
- Prefer explicit env/secrets over hidden defaults.
- Keep CloudFront out of the first pass unless Amplify requires it internally.

## Non-Goals

- Do not implement App Store / Google Play release automation here.
- Do not redesign auth.
- Do not introduce multi-region or high-availability architecture beyond managed AWS defaults.
- Do not migrate old local/dev data unless explicitly needed.
- Do not expose S3 objects publicly.
- Do not make raw bundles public.

## Phase 1: S3 Only

### Goal

Move production media storage to AWS S3 while keeping the current backend and
database deployment model.

### AWS Work

Create an S3 bucket:

- private bucket;
- block public access enabled;
- versioning optional for first pass, recommended before public users;
- server-side encryption enabled;
- CORS configured only for required upload/download methods;
- lifecycle policy for incomplete multipart uploads.

Create IAM access for the backend:

- preferably IAM role when running on AWS later;
- temporary IAM user/access key acceptable for local/backend testing;
- permissions limited to one bucket and prefix.

Suggested object key layout:

```text
media/images/{imageUuid}
```

Rules:

- `imageUuid` is generated by the backend or accepted only if it is a validated client UUID.
- Do not put email, user id, trip id, waypoint id, title or original filename in the S3 key.
- Keep all domain relations in PostgreSQL metadata: user, trip, waypoint, image id and ownership.
- Store `Content-Type` in object metadata and PostgreSQL; S3 key does not need a file extension.
- The bucket remains private.

### Backend Work

Add endpoints:

- `POST /api/media/presign-upload`
  - authenticated;
  - validates trip ownership;
  - accepts file metadata: content type, size, client image id;
  - rejects unsupported content types before presigning;
  - rejects files larger than configured `maxSizeBytes` before presigning;
  - returns presigned PUT URL and storage key.

- `POST /api/media/complete-upload`
  - authenticated;
  - validates trip ownership;
  - verifies that `storageKey` belongs to the authenticated user/trip/waypoint context;
  - runs `HeadObject` against S3 before accepting completion;
  - verifies `Content-Type` when available;
  - verifies `Content-Length` against expected `sizeBytes` when available;
  - only then stores `uploadedAt` and remote metadata in PostgreSQL.

- optional `GET /api/media/presign-download`
  - authenticated/share-aware;
  - returns short-lived GET URL for private image access.

Keep existing backend-proxy image download until the presigned download flow is
confirmed on mobile and web.

Upload limits:

- configure `maxSizeBytes` on the backend;
- configure `allowedContentTypes` on the backend;
- validate both before generating the presigned URL;
- include expected `Content-Type` and `Content-Length` constraints in the upload contract where S3/client support allows it.

Initial suggested values:

```text
MEDIA_UPLOAD_MAX_SIZE_BYTES=10485760
MEDIA_UPLOAD_ALLOWED_CONTENT_TYPES=image/jpeg,image/png,image/heic,image/heif,image/webp
```

### Mobile Work

Change photo upload flow:

1. ask backend for presigned upload URL;
2. upload bytes directly to S3 with `PUT`;
3. call backend `complete-upload`;
4. keep local metadata sync state correct.

Rules:

- retry failed direct upload;
- do not mark image synced before `complete-upload` succeeds;
- send expected `storageKey`, `contentType` and `sizeBytes` to `complete-upload`;
- preserve current local image display from device filesystem;
- restore should still fetch remote images when local files are missing.

### Dev/Postgres Metadata

Metadata can remain in local/dev PostgreSQL in this phase:

- `storageKey`;
- `imageUuid`;
- `contentType`;
- `sizeBytes`;
- `uploadedAt`;
- `uploadStatus`;
- `uploadAttemptCount`;
- `lastUploadError`;
- `remoteVerifiedAt`;
- ownership through trip/user relations.

Suggested upload states:

```text
pending
uploaded
failed
deleted
```

State rules:

- `pending`: metadata exists locally or on server, but S3 upload has not been completed and verified.
- `uploaded`: `complete-upload` succeeded after `HeadObject` verification.
- `failed`: direct S3 upload or `complete-upload` failed; store `lastUploadError` and increment `uploadAttemptCount`.
- `deleted`: object should no longer be visible; physical S3 deletion can be immediate or deferred.

`remoteVerifiedAt` is set only by the backend after successful S3 `HeadObject`
validation. Mobile must not set it directly.

### Acceptance Criteria

- Mobile can upload a waypoint image directly to S3.
- Backend stores metadata after upload completion.
- Restore can download or display the image.
- Shared trip image access remains private and controlled by backend/share rules.
- S3 bucket is not publicly listable or readable.

## Phase 2: RDS PostgreSQL

### Goal

Move production database to managed PostgreSQL.

### AWS Work

Create RDS PostgreSQL:

- private subnet preferred;
- public access disabled if ECS is in the same VPC;
- automated backups enabled;
- deletion protection enabled after initial testing;
- storage autoscaling enabled;
- parameter group only if needed;
- security group allows access only from ECS/backend and admin IP if temporarily required.

### Server Work

Configure:

```text
DATABASE_URL=postgresql://...
```

Run Prisma setup:

- `prisma generate`;
- schema push/migration against RDS;
- verify NestJS can start;
- verify auth, trips, groups, shares, purchases and media metadata.

Because current production data is not important, initial RDS can start empty.

### Acceptance Criteria

- Server works against RDS.
- Mobile login/sync/restore works against RDS-backed server.
- Backup can be created and restored into a separate test database.

## Phase 3: Backend On ECS Fargate

### Goal

Run NestJS backend as a containerized public API.

### Repository Work

Add backend Docker support:

- `server/Dockerfile`;
- production install/build command;
- health endpoint or use existing API health route;
- `.dockerignore`;
- image should not include local `.env`.

### AWS Work

Create:

- ECR repository;
- ECS cluster;
- Fargate task definition;
- ECS service;
- Application Load Balancer;
- target group with health check;
- CloudWatch log group;
- security groups;
- Secrets Manager or SSM Parameter Store values for env/secrets.

Required runtime env/secrets:

- `DATABASE_URL`;
- `JWT_SECRET`;
- `WEB_APP_URL`;
- `WEB_ALLOWED_ORIGINS`;
- `S3_REGION`;
- `S3_BUCKET`;
- optional `S3_ENDPOINT` only for non-AWS S3-compatible storage;
- `MEDIA_UPLOAD_MAX_SIZE_BYTES`;
- `MEDIA_UPLOAD_ALLOWED_CONTENT_TYPES`;
- purchase-related env;
- body limit if still needed.

Prefer IAM task role for S3 access instead of static S3 keys once running in ECS.

### Deployment Work

First version can be manual:

1. build Docker image;
2. push to ECR;
3. update ECS task definition;
4. deploy service.

Later add CI/CD if deployment becomes repetitive.

### Acceptance Criteria

- Public API is reachable over HTTPS through ALB/domain.
- Logs appear in CloudWatch.
- ECS task can access RDS.
- ECS task can access S3 through task role.
- Mobile can login/sync/restore against public API.
- Backend restart does not lose uploaded media or DB data.

## Phase 4: Web On Amplify Hosting

### Goal

Deploy the NextJS web app publicly.

Primary public web use case is now shared trip viewing, not admin.

Implications:

- shared trip pages must load reliably from public links opened in Viber, WhatsApp, Telegram and browsers;
- public share pages should support SSR or server-side data loading where it improves first paint and link preview behavior;
- admin/dashboard pages remain authenticated secondary screens;
- API URLs used by server-side rendering must be available as server env, not only `NEXT_PUBLIC_*`;
- public share pages must not leak raw bundles or private S3 object keys.

### AWS Work

Use Amplify Hosting:

- connect GitHub repository;
- select web app root/build settings;
- set environment variables;
- connect custom domain;
- ACM certificate through Amplify/Route 53 flow.

Required env:

```text
NEXT_PUBLIC_API_BASE_URL=https://api.example.com/api
API_BASE_URL=https://api.example.com/api
NEXT_PUBLIC_GOOGLE_MAPS_API_KEY=...
```

### Web Verification

Check:

- login/auth flow;
- shared trip public PIN page;
- shared trip SSR/server-side loading behavior;
- link preview behavior in Telegram/Viber/WhatsApp where supported;
- in-app shared trip links if applicable;
- API CORS from Amplify domain;
- images on shared/detail screens;
- map rendering and Google Maps key restrictions.

### Acceptance Criteria

- Web loads from production domain.
- Web talks only to production API URL.
- Shared trip web view works with PIN.
- CORS is not permissive beyond required domains.

## Phase 5: Production Hardening

### S3

- Block public access remains enabled.
- Bucket policy allows only backend task role.
- CORS allows only required origins and methods.
- Lifecycle policy for incomplete uploads.
- Consider lifecycle/retention for deleted images.
- Enable access logs or CloudTrail data events later if needed.

### Database

- Automated backups verified.
- Restore drill completed.
- Deletion protection enabled.
- Least-privilege DB user for app runtime if practical.
- Monitor storage, CPU, connections and slow queries.

### Backend

- CloudWatch alarms:
  - ECS task unhealthy/restarts;
  - ALB 5xx;
  - high latency;
  - RDS CPU/storage/connections;
  - S3 4xx/5xx if useful.
- Rate limiting on auth, media presign and public share endpoints.
- Request body limits reviewed.
- CORS locked to production web and mobile needs.
- Structured logs for sync/media failures.
- Secrets stored in AWS-managed secrets, not env files in Git.

### Web

- Google Maps API key restricted by domain.
- Production domain configured.
- Error boundaries/404 for invalid share tokens.
- No dev origins in production config.

### Mobile

- `EXPO_PUBLIC_API_BASE_URL` points to production API for production builds.
- Confirm S3 direct upload on real iOS and Android networks.
- Confirm failed upload retry and offline behavior.
- Confirm restore after fresh install.

### Later

- CloudFront for media or web/API acceleration if needed.
- WAF if public abuse appears.
- Separate staging AWS account or environment.
- CI/CD deployment pipeline.
- Infrastructure as code using Terraform/CDK once the manual shape is validated.

## Suggested Execution Order

1. Implement and test S3 presigned media flow locally against MinIO and then AWS S3.
2. Create RDS and point local/server process at it.
3. Containerize server and deploy to ECS Fargate.
4. Deploy web to Amplify and connect domain.
5. Harden permissions, monitoring and backup/restore.
